# سياسة أمن وتشغيل قاعدة البيانات والسجلات والنسخ الاحتياطية

**النطاق:** RAVEN23 Backend — Phase 03  
**الحالة:** خط أساس أمني موثق؛ إعدادات المزود الإنتاجي وفترات الاحتفاظ تنتظر اعتمادًا صريحًا  
**آخر مراجعة:** 22 نوفمبر 2026

هذه الوثيقة تحدد الضوابط التي يجب أن يلتزم بها أي تشغيل لـRAVEN23 Backend. نجاح CI يثبت سلوك الصورة والشفرة والأدوار التجريبية فقط؛ ولا يثبت إعداد أي مزود إنتاجي لم يتم اختياره وفحصه.

## 1. هويات PostgreSQL ومبدأ أقل صلاحية

يستخدم التطبيق هويتين منفصلتين:

| الهوية | متغير الاتصال | الاستخدام | الصلاحيات المسموحة |
|---|---|---|---|
| تطبيق الويب | `DB_URL` | طلبات API والـcache/session/jobs عند استخدام قاعدة البيانات | CONNECT إلى قاعدة التطبيق، USAGE على schema، CRUD على الجداول، وصلاحيات sequences اللازمة للإدخال |
| مهمة الترحيل | `DB_MIGRATION_URL` | أمر release/migration منفصل فقط | CONNECT وUSAGE وCREATE على schema لتطبيق migrations وامتلاك كائناتها |

كلا الدورين يجب أن يكون:
- `NOSUPERUSER`
- `NOCREATEDB`
- `NOCREATEROLE`
- لا يملك صلاحية إنشاء أدوار أو قواعد بيانات.
- لا يستخدم حساب مالك المنصة أو حساب bootstrap في عملية الويب.

دور التطبيق لا يحصل على CREATE في schema ولا DDL. يمنح دور الترحيل صلاحية CREATE اللازمة وقت release فقط. تُضبط default privileges بحيث يحصل دور التطبيق على CRUD وsequence access على الكائنات التي ينشئها دور الترحيل.

**التحقق في CI:** خدمة PostgreSQL 16 مؤقتة تنشئ الدورين السابقين، وتنفذ migrations بدور الترحيل، ثم تختبر دورة المصادقة وقراءة/كتابة البيانات بدور التطبيق. كما تتحقق من رفض CREATE ROLE وCREATE DATABASE ودخول دور التطبيق بصلاحيات schema محدودة. هذا لا يثبت أن بيانات اعتماد المزود الإنتاجي قد ضُبطت بالطريقة نفسها.

**قاعدة النشر:** يجب توفير سرين مستقلين، وعدم تمرير `DB_MIGRATION_URL` إلى خدمة HTTP. تمرر مهمة release قيمة اتصال الترحيل إلى أمر Artisan في تلك المهمة فقط.

## 2. تشفير اتصال PostgreSQL

- أي اتصال PostgreSQL بعيد في `APP_ENV=production` يجب أن يستخدم `sslmode=require` أو `verify-ca` أو `verify-full`.
- يرفض تحميل إعداد قاعدة البيانات إذا كان المضيف بعيدًا وكانت القيمة `disable` أو `allow` أو `prefer`.
- يسمح بـ`sslmode=disable` فقط لاتصال loopback مثل `127.0.0.1` أو `::1` أو `localhost`؛ وهذا مخصص للتطوير وقاعدة CI المؤقتة.
- إذا كان المزود يقدم CA certificate ويدعم التحقق من اسم المضيف، يفضل `verify-full` بعد اختبار سلسلة الشهادة.
- لا تضع كلمات مرور أو DB URL في logs أو تقارير CI.

## 3. HTTPS وTrusted Proxies

حاوية FrankenPHP تستمع إلى HTTP داخليًا؛ TLS الطرفي يجب أن ينفذ في ingress/load balancer أو reverse proxy الموثوق أمامها.

- يجب أن يوفر مزود الاستضافة HTTPS صالحًا للعميل، ويمنع إرسال بيانات الدخول عبر HTTP العام.
- يظل `TRUSTED_PROXIES` فارغًا ما لم تُعرف عناوين proxy الفعلية؛ عند ضبطه، تسجل IPs أو CIDRs الدقيقة فقط.
- wildcard مثل `*` مرفوض؛ لا تثق في `X-Forwarded-For` من عميل غير موثوق.
- لا يمكن إعلان TLS الطرفي أو عناوين proxy مكتملة قبل فحص إعدادات المزود الفعلية.

## 4. سجلات التطبيق والتشخيص

تخرج سجلات Laravel إلى stderr وسجلات Caddy بصيغة JSON إلى stdout. الحاوية لا تحتفظ بسجل تشغيلي دائم على قرص محلي.

يتم تعطيل Laravel default exception reporter لطلبات API؛ أخطاء API تسجل مرة واحدة فقط عبر renderer مخصص منقح. كما لا يتم الإبلاغ الافتراضي عن QueryException في أي route لتجنب SQL/bindings. الحقول التشخيصية المسموحة محدودة إلى request/correlation ID، method، route template، exception type، source file/line، وSQLSTATE عند الحاجة. يحظر تسجيل:
- كلمات المرور أو رموز الوصول أو رموز التحقق/إعادة التعيين.
- البريد الإلكتروني أو أسماء المستخدمين أو request bodies.
- SQL statements أو bindings أو DB URL أو hostname/schema.
- مفاتيح API أو OAuth secrets أو أي بيانات اعتماد.

تتطلب كل استجابة API معرف طلب `X-Request-ID`، وتظل بيانات الخطأ العامة غير كاشفة. أضيف regression test يتحقق من أن قيم email/password/token ورسالة الاستثناء لا تظهر في سجل Laravel التشخيصي.

**منصة السجلات:** يجب جمع stdout/stderr في خدمة logs لدى المزود أو collector مركزي مع صلاحيات قراءة محدودة وتشفير أثناء النقل والتخزين. لا توجد خدمة collector أو retention settings موثقة حاليًا في Render/Neon.

## 5. سياسة الاحتفاظ بالسجلات

يجب أن يحدد مالك الخدمة قبل الإنتاج:
- مدة الاحتفاظ بسجلات التطبيق العامة.
- مدة الاحتفاظ بأحداث الأمن/المصادقة والتدقيق.
- من يملك صلاحية القراءة والتصدير.
- آلية الحذف عند انتهاء المدة أو طلب حذف البيانات، مع منع ظهور الأسرار في exports.

**القيم الزمنية غير معتمدة بعد.** لم تُخترع مدة مثل 30 أو 90 يومًا؛ يجب أن يعتمد المستخدم المدة المطلوبة قبل ضبطها لدى مزود السجلات. لا تعتبر وجود stdout/stderr دليلًا على وجود retention أو سياسة حذف لدى المزود.

## 6. النسخ الاحتياطية والاستعادة

يجب أن تحقق خدمة قاعدة البيانات قبل أي إنتاج أو cutover:
- backups مشفرة في التخزين والنقل.
- جدولة backup أو PITR معلنة ومراقبة.
- مدة retention محددة ومعتمدة.
- نسخة مستقلة عن دورة حياة حاوية التطبيق، وعدم تخزين النسخة الوحيدة على قرص الخادم.
- صلاحيات backup/restore منفصلة ومحدودة.
- restore rehearsal على قاعدة معزولة، مع التحقق من checksum وعدد السجلات والعلاقات والقيود.
- تسجيل RPO/RTO المحققين في تقرير الاختبار؛ لا يكفي وجود backup object أو نجاح مهمة النسخ.

**القيم الزمنية وRPO/RTO غير معتمدة بعد.** لا توجد أدلة حاليًا على خطة backup فعالة أو استعادة ناجحة لدى مزود الإنتاج؛ يجب فحص الخدمة واختيار cadence/retention/RPO/RTO مع المستخدم قبل اعتبار هذه الضوابط مفعلة.

## 7. قائمة التحقق قبل ربط أي بيئة إنتاجية

- [ ] `DB_URL` يعود إلى دور التطبيق غير المميز.
- [ ] `DB_MIGRATION_URL` يعود إلى دور منفصل، ولا يصل إلى خدمة الويب.
- [ ] دور التطبيق لا يملك SUPERUSER/CREATEDB/CREATEROLE أو CREATE على schema.
- [ ] اتصال PostgreSQL البعيد يفرض TLS موثوقًا.
- [ ] ingress يوفر HTTPS، وTrusted Proxies يقتصر على CIDRs الحقيقية.
- [ ] إعداد log collector وصلاحياته ومدة الاحتفاظ معتمدة ومختبرة.
- [ ] backup schedule/PITR/retention معتمدة، وrestore rehearsal ناجحة مع RPO/RTO.
- [ ] لا أسرار أو بيانات شخصية في logs أو تقارير CI.

## 8. حدود الإثبات الحالي

تم اختبار صورة التطبيق ودوري PostgreSQL منفصلين على قاعدة مؤقتة في GitHub Actions. لم يتم الاتصال بأي قاعدة إنتاجية، ولم تُقرأ قيم secrets، ولم تتغير إعدادات مزود أو يتم نشر التطبيق. لذلك تبقى بنود مزود الإنتاج في القائمة أعلاه متطلبات ما قبل النشر وليست ادعاءات نجاح حالية.

## 9. قرار تأجيل مزودي التشغيل — 27 نوفمبر 2026

بموجب D-050، تؤجل قرارات مزود قاعدة البيانات/الاستضافة والتخزين والسجلات/المراقبة والنسخ الاحتياطي وsecrets/identity والمنطقة والتكلفة إلى ما بعد أعمال Backend المستقلة عن المزود.

- يستمر تطبيق واختبار حدود PostgreSQL roles/TLS وlog redaction وhealth/readiness وbackup/restore synthetic على CI.
- لا يتم إنشاء خدمة logs أو dashboard أو alert destination أو backup service أو KMS/secret manager أو account أو resources خلال هذا التأجيل.
- قيم retention وRPO/RTO والـbackup cadence تبقى غير معتمدة؛ لا تفترض قيمًا ولا تصف ضوابط مزود بأنها مفعلة.
- تظل قائمة ما قبل الإنتاج أعلاه إلزامية بعد اختيار المزود، ولا يجيز D-050 تجاوزها.
