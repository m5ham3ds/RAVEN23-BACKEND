# قواعد المستخدم وقيوده والتعليمات غير القابلة للتجاوز

هذه القواعد ملزمة لكل عمل داخل `m5ham3ds/RAVEN23-BACKEND`. لا يجوز تجاوزها إلا بطلب مباشر وصريح ومحدد من المستخدم يغير القاعدة المعنية. الموافقة العامة على مواصلة التطوير لا تعني السماح بإجراء تدميري أو لمس بيانات الإنتاج.

## 1. المحافظة على العمل الحالي
1. ممنوع البدء من الصفر لمجرد أن المشروع يحتاج إلى إعادة تنظيم.
2. يجب الحفاظ على منطق المصادقة والحسابات ومعرّفات المستخدمين والجلسات والمigrations والـAPI contracts والاختبارات الناجحة ما لم يثبت وجود عيب محدد.
3. قبل تغيير سلوك حالي، حدد المستهلك، والسلوك الحالي والمتوقع، والاختبارات، وأثر قاعدة البيانات.
4. ممنوع إعادة تنفيذ مرحلة مكتملة أو تكرار عمل منجز دون سبب مسجل.
5. يجب الاستمرار من آخر commit وتقرير مرحلة تم التحقق منهما، لا من نسخة قديمة أو تخمين.
6. لا تفحص أو تعدل مستودعات أو أرشيفات غير مرتبطة إلا بتوجيه مباشر.

## 2. بيئة المستخدم وطريقة العمل
1. بيئة التطوير الأساسية هاتف Android؛ لا تفترض توفر PC.
2. فضّل GitHub Web وGitHub Actions وTermux، واجعل البناء والاختبارات الثقيلة على CI متى أمكن.
3. لا تجعل أداة GUI مكتبية شرطًا غير معلن لإنجاز مرحلة.
4. عند الإبلاغ عن تغيير، اذكر المسارات والفرع وcommit SHA وروابط workflow ونتائج الاختبارات.
5. وثائق الخطة والتقارير الموجهة للمستخدم تكون بالعربية الواضحة، مع إبقاء أسماء الملفات والمصطلحات البرمجية بالإنجليزية.

## 3. حماية البيانات — قواعد مطلقة افتراضيًا
1. ممنوع حذف أو تفريغ أو إعادة إنشاء قاعدة الإنتاج أو جداول المستخدمين.
2. ممنوع حذف حساب حقيقي أو password hash أو Google identity أو token/session أو favorite أو history أو progress أو subscription أو ملف مستخدم.
3. ممنوع تنفيذ أوامر مدمرة على قاعدة حية مثل `migrate:fresh` أو `db:wipe` أو `DROP TABLE` أو `TRUNCATE` أو `DELETE` غير محدد.
4. يمنع توجيه CI أو اختبارات integration إلى قاعدة Neon/RDS الإنتاجية؛ استخدم PostgreSQL مؤقتًا أو staging معزولة.
5. لا تنفذ اختبارات إنشاء/حذف حساب إنتاج إلا ببيانات اصطناعية واضحة وفريدة، وموافقة مباشرة، وخطة cleanup يمكن التحقق منها. الأفضل staging.
6. قبل أي migration أو نقل إنتاجي: backup متسق ومشفّر، والتحقق من سلامته، وتجربة restore إلى قاعدة معزولة، ثم موافقة المستخدم.
7. حافظ على IDs والعلاقات الصحيحة. اجعل migrations additive أو reconciliations مدروسة؛ لا تسمح لتراجع Migration بمحو الهوية أو الجلسات.
8. وجود backup task لا يعني سلامة البيانات؛ يجب إثبات نجاح الاستعادة فعليًا.

## 4. الأسرار والخصوصية
1. ممنوع رفع `.env` أو DB URLs أو AWS credentials أو API secrets أو OAuth secrets أو private keys أو bearer tokens أو passwords أو بيانات مستخدمين إلى Git.
2. لا تطبع قيم الأسرار في logs أو التقارير أو screenshots أو المحادثة.
3. وثّق أسماء الأسرار ووظيفتها فقط، لا قيمها.
4. استخدم temporary least-privilege credentials، وOIDC من GitHub إلى AWS عند النشر.
5. لا تضعف المصادقة أو authorization أو TLS أو rate limits لتجاوز فشل اختبار.

## 5. النشر والتكاليف
1. لا تنشئ حساب AWS أو موارد أو خدمات مدفوعة نيابة عن المستخدم.
2. لا تفترض أن أرصدة Free Tier دائمة أو أن مواردها كافية؛ تحقق من شروط المنطقة والسعر المستمر قبل النشر.
3. لا تنقل الإنتاج من Render/Neon حتى تنجح الاستعادة والاختبارات ويوافق المستخدم مباشرة.
4. اجعل API hostname ثابتًا ومستقلًا عن عنوان الخادم متى أصبح النطاق متاحًا.
5. تغيير الخادم يجب ألا يتطلب إعادة كتابة منطق التطبيق أو Android.
6. لا تخزن مكتبة الفيديوهات على قرص نظام الخادم.

## 6. نطاق المنتج والقرارات
1. نطاق العمل RAVEN23 فقط.
2. لا تضف لوحة إدارة أو نظامًا تجاريًا أو خدمة غير مطلوبة دون سبب وقرار واضح.
3. لا تخترع طرق دفع أو أسعارًا أو شروط اشتراك أو مزود خدمة من تلقاء نفسك.
4. اعتبر استخدام Android الحالي للـAPI عقد توافق يجب التحقق منه قبل تغيير المسارات أو response fields.
5. حافظ على قواعد المنتج المتفق عليها. إذا كان قرار معين يمنع التنفيذ ولا يمكن وضع افتراض آمن، اطرح سؤالًا مباشرًا واحدًا فقط.

## 7. الصدق في تقارير الحالة
1. افصل بين: كود نُفذ، اختبارات آلية نجحت، تكامل staging تحقق، وتجربة جهاز حقيقي/إنتاج تحققت.
2. لا تصف ميزة بأنها تعمل لأن الكود يترجم أو mock test يمر.
3. اذكر الفشل والإلغاء بوضوح، ولا تخفهما خلف تشغيل أحدث ناجح.
4. سجل commit SHA الذي اختُبر. نجاح SHA قديم لا يثبت SHA أحدث.
5. إذا لم تتوفر صلاحية أو أداة لتنفيذ خطوة، اذكر ذلك ولا تدّع نجاحها.

## 8. الاستثناءات
لا يلغي أي قاعدة إلا طلب مباشر ومحدد. العمليات التدميرية أو تغيير الأسرار أو تكاليف السحابة أو production cutover تتطلب تأكيدًا مباشرًا يسمي المورد والإجراء. الموافقة العامة على الخطة أو على مرحلة مختلفة ليست تصريحًا بذلك.

## 9. تأجيل اختيار جميع مزودي الخدمات — قرار المالك 27 نوفمبر 2026

1. لا تطلب من المستخدم الآن اختيار مزود استضافة أو قاعدة بيانات أو تخزين أو بريد أو Push أو دفع أو registry أو secrets/identity أو monitoring/logs أو DNS/edge أو region أو خطة أو ميزانية.
2. تؤجل جميع هذه الاختيارات إلى ما بعد إكمال أعمال Backend التي يمكن تنفيذها واختبارها دون حساب أو credential أو مورد خارجي.
3. استمر في تنفيذ Laravel/API/schema/migrations/contracts/feature code واختبارات SQLite/PostgreSQL وS3Mock/fakes وprovider-neutral architecture وCI وsynthetic rehearsals.
4. لا تضف provider-specific SDK/sender/payment adapters أو credentials/secrets/accounts/resources/remote backend/terraform apply/registry push/DNS change/staging or production deployment قبل إعادة فتح القرار وموافقة صريحة على نطاق المورد والتكلفة.
5. لا تحول أي مرحلة إلى COMPLETE لمجرد تأجيل اعتماديتها؛ افصل تنفيذ الكود ونجاح CI عن إثبات التكامل الحقيقي في staging/device/provider.
6. عند اكتمال الأعمال المحايدة، جهز مقارنة مشتركة ومحدثة للمتطلبات والأمن والخصوصية والتكلفة والاعتمادية وقابلية الخروج، ثم اطلب موافقة مستقلة قبل كل مورد أو عملية مدفوعة أو cutover.
7. هذا القرار D-050 يوسع التأجيل السابق الخاص بـPush ولا يلغي قواعد حماية البيانات أو موافقة production cutover.

## D-051 — توقيت إعادة فتح القرار بعد نهاية الخطة كاملة

لا يُطلب اختيار أي مزود أو منطقة أو خطة أو تكلفة عند إنهاء هذه المرحلة منفردة. جميع اختيارات المزودين تُؤجل إلى ما بعد الانتهاء النهائي من خطة تطوير Backend بالكامل. حتى ذلك الوقت يستمر العمل المحايد الذي لا يحتاج مزودًا، وتبقى معايير القبول التي تستلزم مزودًا حقيقيًا أو staging/production operation مؤجلة ولا تُسجل COMPLETE. راجع phases/DECISIONS.md (D-050 وD-051).
