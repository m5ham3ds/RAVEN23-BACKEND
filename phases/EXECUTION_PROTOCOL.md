# بروتوكول التنفيذ الإلزامي وإغلاق المراحل

يجب اتباع هذا البروتوكول في كل مرحلة وكل إصلاح لاحق.

## 1. قبل تعديل الكود
1. اقرأ `STATUS.md` و`MASTER_PLAN.md` وقواعد المستخدم ومواصفة المرحلة وآخر تقرير.
2. تحقق من الفرع الحالي وSHA الخاص بـ main والـSHA المستهدف وآخر CI.
3. افحص الملفات والاختبارات والمستهلكين المرتبطين فقط بالعمل الحالي.
4. حدد الملفات والـAPI والجداول والسلوكيات المتأثرة.
5. سجل مخاطر البيانات والأمن والتوافق والتراجع.
6. إذا كانت الاعتماديات ناقصة، سجّل WAITING_DEPENDENCY ولا تتظاهر بأن المرحلة جاهزة.
7. إذا كان المطلوب قرارًا أو حسابًا أو secret من المستخدم، سجّل WAITING_EXTERNAL وأكمل فقط العمل المستقل عنه.

## 2. قواعد التغيير
- التزم بـ`BRANCH_POLICY.md`: ثلاثة فروع دائمة فقط. تغييرات التطبيق والـmigrations والوثائق على `main` بcommits صغيرة؛ الاختبارات العامة فقط على `RAVEN23-BACKEND-TEST` واختبارات الحسابات فقط على `RAVEN23-BACKEND-USERS`. لا تنشئ feature/phase branches أو PRs إضافية.
- اجعل commits صغيرة ومحددة.
- لا تخلط refactoring غير المرتبط مع تغيير وظيفة للمستخدم.
- فضّل migrations تدريجية وAPI compatibility.
- أضف الاختبارات مع تغيير السلوك.
- لا تغيّر response contract المستخدم في Android بصمت.
- الأسرار runtime-only؛ ملف `.env.example` يحتوي placeholders.
- افصل adapters الخاصة بالمزود عن domain logic.
- عند الفشل شخّص السبب الحقيقي ثم أكمل من الحالة المثبتة؛ لا تعِد المشروع من البداية ولا تكرر المنجز.

## 3. مستويات الاختبار المطلوبة بحسب نطاق المرحلة
1. Formatting وstatic checks.
2. PHP syntax وComposer validation.
3. Unit/Feature tests.
4. PostgreSQL integration على قاعدة معزولة.
5. Migrations على قاعدة اختبار فارغة.
6. ترقية schema سابقة ممثلة ببيانات اصطناعية.
7. API contract tests لمسارات Android المستخدمة.
8. Docker build وruntime smoke.
9. فحص dependencies/secrets/container/security حسب النطاق.
10. staging أو real-device للتحقق من OAuth والبريد والإشعارات والتخزين والتصرفات الخاصة بـ Android.

إذا تم تخطي اختبار مطلوب، اشرح السبب في تقرير المرحلة.

## 4. حالات المرحلة الرسمية
- **NOT_STARTED:** لم يبدأ التنفيذ.
- **IN_PROGRESS:** التنفيذ جارٍ.
- **BLOCKED:** يوجد عائق يمنع الاستمرار.
- **WAITING_DEPENDENCY:** العمل ينتظر مخرجات مرحلة أخرى.
- **WAITING_EXTERNAL:** ينتظر حسابًا أو secret أو DNS أو جهازًا أو موافقة أو مزود خدمة.
- **PARTIAL:** جزء من النطاق اكتمل ومعايير أخرى لم تكتمل.
- **COMPLETE:** كل معايير القبول تحققت مع أدلة.
- **SUPERSEDED:** تم استبدال النطاق بقرار جديد موثق.

لا تستخدم كلمة "اكتملت" دون مطابقة تعريف COMPLETE وإرفاق الدليل.

## 5. تقرير كل مرحلة
عند إكمال المرحلة أو تعليقها أو حظرها، أنشئ ملفًا جديدًا:
`phases/reports/PHASE-XX-REPORT-YYYY-MM-DD.md`

يجب أن يحتوي:
- اسم المرحلة وحالتها وتاريخ البدء والإغلاق.
- SHA الأساس وSHA النهائي الذي اختُبر.
- الفرع وPR والـcommits.
- الملفات التي تغيرت.
- ما تم وما لم يتم ولماذا.
- الوظائف القديمة التي حُفظت.
- الاختبارات ونتائجها وروابطها.
- حالة قاعدة البيانات وحماية البيانات.
- العيوب والمخاطر والعوائق.
- ما ينتظر مرحلة أخرى أو إجراء المستخدم.
- معايير القبول PASS/FAIL/NOT TESTED.
- المرحلة التالية المسموح بها ولماذا.
- تعليمات دقيقة لاستكمال العمل دون تكرار.

لا تنشئ تقرير اكتمال مزيف قبل التنفيذ. يمكن إنشاء تقرير PARTIAL/WAITING/BLOCKED عند التوقف.

## 6. تحديث الحالة
بعد كل تغير مهم:
- حدّث `STATUS.md`.
- حدّث صف المرحلة في `MASTER_PLAN.md`.
- أضف القرار الجديد في `DECISIONS.md` بدل حذف القرار القديم.
- حافظ على كل التقارير السابقة؛ صحح الأخطاء بتقرير addendum جديد.

## 7. التعامل مع فشل CI
1. حدد workflow/run/job/step/commit SHA بدقة.
2. صنف السبب: source defect أو test defect أو outage خارجي أو credentials/config أو infrastructure limit أو flaky test.
3. أصلح السبب المثبت فقط.
4. أعد تشغيل failed job عندما يكون آمنًا ومتاحًا؛ وإلا أنشئ run جديدًا على commit المصحح.
5. أعد الاختبارات التابعة.
6. لا تغلق المرحلة قبل نجاح SHA المصحح.
7. لا تستخدم retry loops عشوائية لإخفاء السبب.

## 8. بوابة بيانات الإنتاج
- backup متسق ومشفّر.
- تحقق من metadata/checksum.
- restore إلى قاعدة مستقلة وتجربة الاستعادة عمليًا.
- مقارنة أعداد السجلات والمعرفات والعلاقات والقيود.
- التخطيط للكتابات المتزامنة أثناء النقل: freeze أو delta capture أو dual-write مدروس.
- تجربة migrations على clone.
- موافقة المستخدم المباشرة تحدد المصدر والهدف والوقت.
- إبقاء المصدر سليمًا وتعريف trigger وخطوات rollback.
- بعد cutover تحقق من login/profile/favorites/history/progress/sync والميزات المفعلة.

## 9. نزاهة النتائج
الاختبار الفاشل لا يسجل PASS. الوظيفة الملغاة CANCELLED وليست نجاحًا أو فشلًا. Workflow على commit قديم لا يثبت commit جديدًا. نجاح Docker build لا يعني جاهزية الإنتاج. ونجاح staging لا يثبت عمل مزود خارجي ما لم يُختبر ذلك المسار.


## 10. حوكمة الفروع الحالية — 23 نوفمبر 2026

- الفروع الوحيدة: `main`, `RAVEN23-BACKEND-TEST`, `RAVEN23-BACKEND-USERS`.
- تعليمات الفروع المخصصة/PR في التقارير القديمة تاريخية وقد superseded بها BRANCH_POLICY.
- لا تنشئ phase/feature branch. عند تعطل CI سجّل SHA/run/job/log evidence، وأصلح على الفرع الدائم نفسه.
