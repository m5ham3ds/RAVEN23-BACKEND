# المرحلة 11 — تجهيز AWS والبنية السحابية والنشر الآلي

**الحالة:** WAITING_EXTERNAL — إنشاء الحساب والموافقة على التكاليف  
**الاعتماديات:** المرحلتان 02 و03، المرحلة 08 عند الحاجة للتخزين، والمرحلة 10

## الهدف
تجهيز بيئة AWS قابلة لإعادة الإنشاء والنشر من GitHub، مع إبقاء التطبيق وقاعدة البيانات والملفات قابلة للنقل.

## العمل
1. عند جاهزية المستخدم: تحديد الحساب والمنطقة الجغرافية والميزانية والتنبيهات وحدود الإنفاق.
2. مقارنة EC2/RDS/S3/Redis أو بدائلها وفق أحجام فعلية وتكلفة التشغيل بعد التجربة.
3. كتابة Infrastructure as Code وتوثيق كل مورد ومخرجاته.
4. إعداد VPC/subnets/security groups وفق أقل صلاحية؛ DB لا تكون عامة.
5. إعداد IAM role لـ GitHub OIDC بشروط repository/branch/environment محددة.
6. منع نشر main إلى production دون required checks وموافقة environment.
7. بناء image مرة واحدة ونشر digest نفسه عبر registry مختار.
8. إعداد secrets من Secrets Manager أو SSM مع صلاحيات تشغيل محدودة.
9. إعداد TLS/API domain، reverse proxy، health/readiness، logs/metrics/alerts.
10. إنشاء PostgreSQL staging مستقل واختبار migrations وrestore عليه.
11. إعداد S3 buckets خاصة مع encryption/lifecycle/versioning حسب الحاجة والميزانية.
12. توثيق إيقاف الموارد والنسخ الاحتياطية وتكاليف الخمول لمنع مفاجآت الفاتورة.

## معايير القبول
- كل مورد قابل لإعادة الإنشاء من IaC ومراجعته.
- GitHub ينشر باستخدام OIDC، دون AWS access keys ثابتة في repository secrets.
- لا قاعدة بيانات عامة؛ الوصول محصور بالخادم/المسارات اللازمة.
- staging health وdatabase schema وauth/sync smoke ناجحة.
- تنبيهات الميزانية والرصد تعمل.
- التكاليف المتوقعة والمستمرة معتمدة من المستخدم.

## ممنوع
لا تنشئ أو تشغل موارد فعلية أو تدفع أموالًا قبل موافقة المستخدم. لا تعتبر فترة free tier وعدًا باستضافة دائمة مجانية.
